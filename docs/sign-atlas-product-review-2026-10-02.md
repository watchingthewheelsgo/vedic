# Sign Atlas 产品、界面与技术评审

本轮以本地代码、线上页面与官方 Agent SDK 文档为依据。已查看首页、个人中心、出生资料、八字录入和管理权限页；报告及管理详情审查为代码层面，未用真实付费报告完整走通所有分支。不能把构建通过当作所有外部集成验收通过。

## 判断

目前具备排盘、报告、校时、登录、付费和问答的底层能力，但尚不是成熟的持续服务产品。过去的主要路径是“首页 → 填较多出生资料 → 等待报告 → 离开”，个人中心也主要是报告仓库。成熟度应看首次价值是否容易获得、异常能否恢复、依据是否透明、隐私是否可控、用户是否有健康的持续使用理由，而不是看 Agent 数量或报告长度。

本轮改成两个并行入口：

1. 我的日常：登录 → 查看当天干支 → 记录事件与心情 → 选择要问的事情 → 三视角反思 → 回看行动和自己的记录。
2. 深度读盘：出生资料 → 确定时间可信度 → 排盘/必要时校时 → 证据约束的报告 → 关联到日常问题。

用户无需提供出生资料才能开始记录。日记事实、历法事实、传统解释、AI建议应分层展示；不把“AI时代”理解成每一个按钮都触发一个 Agent。

## 本轮个人空间能力

- 当地日期、时区、当日干支、天干和地支五行。由 lunar-python 计算，不由模型编造；采用民用日期午夜换日，不冒充完整个人八字，也未做真太阳时换算。
- 每日一条可编辑记录：1–5心情、生活领域、自由文字。可选历史日期，保存到服务端数据库。
- 时间线、按天干/地支/日柱观察心情均值与样本数。每组不足7日不展示均值；7日只是保守的展示门槛，不代表统计显著性。未记录日不当作心情为零。
- 问答基于所选的一天，可选关联本人拥有的 Vedic 排盘；不自动发送其他日记。保存问题、回答、当时日记快照和抽牌结果。
- 八字视角基于日干支，不声称已经做完本命喜用神；Vedic 没有命盘时明确为一般反思；塔罗是从22张大阿尔卡纳随机抽一张正位，属于象征反思，不是78张牌阵产品。
- 每个视角输出解释与可尝试行动，另有一个回顾问题。不是确定性的吉凶、医疗、投资或他人心理预测。
- 所有读取/写入/删除/命盘关联都验证用户归属。删除带确认。可导出当前窗口的记录；首版列表/统计窗口最多365个最近记录日，老日期可按日期读取。
- UI支持中/英/日；干支本身保留中文历法符号。部分历法分组/塔罗牌名保留英文。

### 还应继续迭代的功能

1. 行动回访：把“我准备试什么”变成可勾选的小行动，几天后记录实际体验，而不是继续索取预测。
2. 周回顾：用户选中记录后生成主题总结，明确哪些句子来自原始记录、哪些是模型解释。
3. 自定义标签、睡眠/精力/压力自评，用星期、生活事件、样本分布一起解释观察，减少选择性记忆。
4. 更完整的数据导出/恢复、保存期限、删除及AI提供商说明；提醒必须由用户选择开启，不制造断签焦虑。
5. 真实个人八字关联、Vedic当日行运计算、78张塔罗与多牌阵应分别验收，不能共用通用提示词然后宣称三个引擎全支持。

## Claude Agent SDK + Skills 是否适合

**适合深度工作流，不适合作为每次日常交互的唯一执行引擎。** 不建议推倒重写。

可保留：确定性排盘 → 类型化事实 → 可版本化 Skills → 报告生成/取证/审查；已有 calculator、schemas、core job checkpoints、tool allowlist、超时和日志是好的基础。

应分层：

| 工作                                 | 推荐执行方式                                 |
| ------------------------------------ | -------------------------------------------- |
| 日历、干支、排盘、权限、持久化、统计 | 普通后端函数 + 数据库                        |
| 日记反思、摘要、短问答               | 有输入边界和输出 schema 的无工具单次模型请求 |
| 深度报告、校时、多步骤取证           | Agent SDK + 版本化 Skills + 任务状态         |
| 支付、额度、账号归属                 | 后端强制执行，不能交给模型判断               |

本轮日记采用无工具模型调用、输出Pydantic校验、50秒超时、每实例2个并发、每条记录最多8次解读及请求ID幂等。它不会把日记目录开放给 Agent。当前并发控制适用于现有单进程部署；多worker前应换为共享配额/队列，不能把进程内信号量当分布式限流。

### 仍需处理的技术风险

- **P1，隔离边界**：旧 `run_skill_prompt_task` 某些路径以项目根目录作为 cwd 并启用 Read/Glob/Grep；`run_skill_task`有Write/Edit。仅声明“只读本workspace”并非操作系统隔离。应使用每任务容器/只挂载必要事实与技能、只读资源、禁止访问应用secret和其他用户session。此次没有对线上多租户越权进行利用测试，不把风险说成已发生泄漏。
- **P1，任务与恢复**：CoreJobRuntime 用内存 registry + asyncio.create_task。已有持久化快照、恢复和断点，不能说“完全无恢复”；但它还不是持久队列/分布式lease。多进程会产生重复执行风险，需要任务claim、lease、幂等输出和取消语义。
- **P1，预算**：深度报告存在 max_turns/timeout，但没有统一按用户/任务的实际token、费用预算。应记录预算、模型/skill/calculator版本、失败类型与重试，代理兼容端点的费用字段可能为空。
- **P1，隐私运营**：日记是更敏感的数据类型，发布规模扩大前需补全隐私政策、提供商处理范围、备份保留和删除策略。数据库私有网络不等于端到端加密。
- **P2，数据库readiness**：旧health主要检查配置/初始化标志；迁移检查只看alembic_version表存在，不等于到达head。应增加实际数据库查询与版本检查。
- **P2，用户并发初始化**：UserStore先查再插且用户ID唯一，多请求首次登录存在竞争。需要数据库upsert或冲突后读取，不应靠前端串行请求掩盖。
- **P2，模型适配**：Claude Agent SDK承载DeepSeek兼容环境。协议兼容不代表所有skills、structured output、工具权限、reasoning参数的语义完全相同；每个提供商必须做契约测试。

Anthropic也建议先用简单、可组合流程，只有任务确实需要动态决策时才增加Agent复杂度；其安全文档区分权限控制与真正隔离：

- https://www.anthropic.com/engineering/building-effective-agents
- https://code.claude.com/docs/en/agent-sdk/secure-deployment
- 历法库：https://github.com/6tail/lunar-python
